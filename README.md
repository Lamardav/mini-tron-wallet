# Mini TRON Wallet

Кастодиальный кошелёк TRON в тестовой сети Nile: регистрация создаёт пользователю адрес, приложение показывает баланс и историю, позволяет отправить TRX и следит за подтверждением транзакции в блокчейне.

**Стек:** Flutter Web + Riverpod, NestJS + TypeScript, PostgreSQL + Prisma, TRON Nile через Chainstack, Kafka, Docker Compose.

```
Flutter Web  -->  REST  -->  NestJS  -->  PostgreSQL
                               |
                               +-->  Chainstack  -->  TRON Nile
                               +-->  Kafka (outbox)
```

Фронтенд не обращается к базе и к Chainstack напрямую и никогда не получает приватные ключи: он знает только про REST API бэкенда.

## 1. Как запустить проект

Нужны Docker и Docker Compose. Всё остальное поднимается контейнерами.

```bash
cp .env.example .env
```

Заполните в `.env`:

| Переменная | Чем заполнить |
|---|---|
| `JWT_SECRET` | `openssl rand -hex 32` |
| `WALLET_MASTER_KEY` | `openssl rand -hex 32`, ровно 64 hex-символа |
| `CHAINSTACK_ENDPOINT` | `https://tron-nile.core.chainstack.com` |
| `CHAINSTACK_API_KEY` | ключ проекта Chainstack |

Соберите фронтенд и поднимите стек:

```bash
cd frontend && flutter build web --release && cd ..
docker compose up -d --build
```

Поднимутся пять сервисов: `postgres`, `kafka`, `backend` (применяет миграции при старте), `consumer`, `frontend` (nginx отдаёт собранный Flutter и проксирует `/api` на бэкенд). Приложение открывается на `http://localhost`.

### Разработка без Docker

Если Docker недоступен локально, базу и Kafka можно держать на сервере и пробросить порты:

```bash
bash scripts/tunnel.sh
```

После этого `DATABASE_URL` и `KAFKA_BROKERS` со значением `localhost` работают с удалёнными сервисами.

### Как устроен Riverpod

Состояние живёт в трёх провайдерах (`frontend/lib/providers/`):

- `authProvider`, это `Notifier<AuthState>`: восстановление сессии по сохранённому JWT, вход, регистрация, выход. Провайдер живёт всё время работы приложения, поэтому сессия переживает навигацию.
- `walletProvider`, это `Notifier<WalletState>` с `isAutoDispose: true`: баланс, история и отправка. Внутри `build()` открывается цикл long-polling, а `ref.onDispose` останавливает его, когда экраны кошелька закрыты.
- `themeProvider` отвечает за переключение светлой и тёмной темы с сохранением выбора.

Маршрутизация на `go_router`: экраны `/login` и `/register` открыты, а `/wallet`, `/send` и `/transactions` живут внутри `ShellRoute` с общей шапкой. Роутер создаётся один раз, а на изменения сессии реагирует через `refreshListenable`, поэтому навигация не сбрасывается при входе и выходе.

## 5. Как запустить PostgreSQL

```bash
docker compose up -d postgres
cd backend && npx prisma migrate deploy
```

### Почему Prisma

ТЗ разрешает любую ORM, выбрана Prisma по трём причинам. Миграции здесь первичны: схема описывается декларативно, `prisma migrate` порождает обычный SQL-файл, который лежит в репозитории и разворачивается одной командой. Сгенерированный клиент типизирует запросы вплоть до имён колонок, поэтому переименование поля ломает сборку, а не продакшен. И `BigInt` из схемы отображается в `bigint` TypeScript без промежуточных чисел с плавающей точкой, для денег это решающий аргумент.

### Схема

- `users`: `id`, `email` (уникальный), `password_hash`, `created_at`.
- `wallets`: `user_id` (уникальный, внешний ключ), `address` (уникальный), `encrypted_private_key`.
- `transactions`: `id`, `user_id` (внешний ключ), `direction`, `amount`, `address`, `status`, `tx_hash`, `idempotency_key`, `fee`, `balance_before`, `balance_after`, `block_number`, `created_at`.
- `outbox_events`: события для Kafka.
- `sync_state`: последний просканированный блок.

Ограничения, которые несут смысл: `UNIQUE(user_id, idempotency_key)` защищает от повторной отправки, `UNIQUE(user_id, tx_hash, direction)` защищает от повторной записи одного и того же перевода, индексы по `status` и по `(user_id, created_at DESC)` обслуживают воркер подтверждений и выдачу истории.

## 6. Как создаётся TRX wallet

При `POST /auth/register` бэкенд генерирует пару ключей через TronWeb, сохраняет base58-адрес в `wallets.address`, шифрует приватный ключ и кладёт в `wallets.encrypted_private_key`. Пользователь получает JWT и свой адрес. Все обращения к сети идут через Chainstack: `CHAINSTACK_ENDPOINT` и `CHAINSTACK_API_KEY` собираются в `fullHost` клиента TronWeb.

## 7. Как хранятся private keys

Приватный ключ шифруется AES-256-GCM мастер-ключом `WALLET_MASTER_KEY` из `.env`. В базе лежит строка `iv.tag.ciphertext` в base64: случайный вектор инициализации на каждое шифрование и тег аутентификации, из-за которого подмена шифротекста приводит к ошибке расшифровки, а не к молчаливому мусору.

Ключ расшифровывается только в момент подписи транзакции и не покидает бэкенд: его нет в ответах API, нет во Flutter и нет в логах. В Git попадает только `.env.example` без значений.

## 8. Как отправляется TRX

`POST /wallet/send` выполняет шаги по порядку:

1. проверяет JWT;
2. проверяет корректность адреса получателя и запрещает перевод на собственный адрес;
3. разбирает сумму и отвергает то, что сеть не сможет провести;
4. если такой `Idempotency-Key` уже был, возвращает прежнюю транзакцию и на этом останавливается;
5. собирает транзакцию, считает комиссию и сверяет баланс с суммой перевода **вместе с комиссией**;
6. создаёт запись со статусом `pending`;
7. подписывает транзакцию и **сохраняет `tx_hash` до отправки в сеть**;
8. отправляет транзакцию и возвращает ответ фронтенду.

Порядок седьмого и восьмого шагов выбран намеренно: если соединение оборвётся во время отправки, хеш уже сохранён, и воркер подтверждений сам выяснит судьбу транзакции по сети. Ошибка подписи переводит запись в `failed`, ошибка сети оставляет `pending`.

Входящие переводы находит отдельный воркер: он идёт по новым блокам, отбирает переводы на известные адреса и заводит записи с направлением `incoming`.

### Комиссия показывается до отправки

Перед подтверждением перевода фронтенд запрашивает `POST /wallet/estimate`, и пользователь видит, сколько получит адресат, сколько возьмёт сеть и сколько спишется всего. Оценка строится на реальных данных: бэкенд собирает транзакцию, измеряет её размер, читает остаток бесплатного дневного трафика отправителя и берёт из параметров сети цену байта и стоимость активации адреса.

Практически это три разных исхода, и все они встречаются:

| Ситуация | Комиссия |
|---|---|
| Хватает бесплатного трафика, адресат активен | 0, подпись «free, covered by your daily bandwidth» |
| Трафик исчерпан | размер транзакции, умноженный на цену байта |
| Адресат ни разу не использовался | плюс 1 TRX за активацию адреса |

Последний случай особенно важен: TRON молча списывает 1 TRX за создание нового аккаунта, и без предупреждения это выглядит как пропавшие деньги. В интерфейсе такой перевод помечается отдельной строкой.

Та же оценка используется и на сервере при отправке: перевод отклоняется, если баланса не хватает на сумму вместе с комиссией. Клиентской оценке сервер не доверяет, потому что её тривиально подделать.

### Обновления в реальном времени

Вместо опроса каждые 5 секунд используется long-polling: `GET /wallet/updates?since=N` держит запрос до 25 секунд и отвечает сразу, как только состояние кошелька меняется. Бэкенд хранит в памяти счётчик версии на пользователя и увеличивает его при отправке, при подтверждении транзакции воркером и при обнаружении входящего перевода. Клиент, получив ответ, немедленно открывает следующий запрос.

Почему не SSE и не WebSocket: `EventSource` не умеет передавать заголовок `Authorization`, то есть JWT пришлось бы класть в query-строку и светить его в логах nginx, а WebSocket ради односторонних уведомлений это избыточная инфраструктура. Long-polling остаётся обычным запросом с заголовком и укладывается в разрешённый ТЗ polling, давая при этом задержку в доли секунды.

Ограничение честно называется: счётчик версий живёт в памяти процесса, поэтому при горизонтальном масштабировании его нужно вынести в Redis или подписать инстансы на тот же Kafka-топик. Для одного инстанса, как здесь, этого достаточно, а на отказ клиент реагирует повтором через 3 секунды.

### Детали транзакции

Клик по строке в истории открывает окно с полной картиной операции: сумма, отправитель или получатель, фактическая комиссия, итог списания, баланс до и после, дата, номер блока, хеш транзакции и ссылка на Tronscan. Адрес и хеш копируются одним нажатием.

Баланс до и после это не расчёт на глаз: при отправке сохраняется наблюдённый баланс перед подписью, а при подтверждении воркер записывает фактическую комиссию из сети, номер блока и баланс, снятый в этот момент. Недостающая половина выводится из остальных. Для входящего перевода комиссия помечена как оплаченная отправителем, потому что получатель за неё не платит.

## 9. Как работает idempotency

Заголовок `Idempotency-Key` обязателен. Ключ пишется в ту же строку таблицы `transactions`, что и сама операция, под уникальным индексом `UNIQUE(user_id, idempotency_key)`.

Повторный запрос с тем же ключом находит существующую запись и возвращает её, не обращаясь к блокчейну. Если два запроса пришли одновременно и оба не нашли записи, вставку выиграет ровно один: второй получит ошибку уникальности `P2002`, перечитает запись победителя и вернёт её. Подписывает и отправляет транзакцию только тот запрос, который создал строку, поэтому в сети всегда оказывается одна транзакция.

Фронтенд генерирует ключ один раз на попытку отправки и переиспользует его при повторе, так что повторное нажатие кнопки не создаёт второй перевод.

## 10. Как обрабатывается конвертация TRX

Внутренняя единица это nanoTRX, `1 TRX = 1 000 000 000 nanoTRX`, как требует ТЗ. Суммы везде целые и передаются строками: во Flutter это `BigInt`, в JSON строка, в NestJS `bigint`, в PostgreSQL `bigint`. Чисел с плавающей точкой в денежном пути нет ни в одном слое.

**Важное расхождение, о котором стоит сказать прямо.** Сеть TRON оперирует единицей SUN, где `1 TRX = 1 000 000 SUN`, то есть поддерживает шесть знаков после запятой, а не девять. Сумма вида `0.123456789 TRX` физически не может быть проведена в TRON. Поэтому система устроена так:

- формат ТЗ сохранён: внутри всё считается в nanoTRX и отображается с девятью знаками;
- пересчёт nanoTRX в SUN и обратно выполняется только в блокчейн-адаптере, на границе с сетью;
- сумма, не кратная 1000 nanoTRX, отклоняется с ошибкой `AMOUNT_NOT_REPRESENTABLE_ON_CHAIN` до всякого обращения к сети: лучше честно отказать, чем отправить не то, что попросили;
- интерфейс принимает не более шести знаков и показывает последние три разряда суммы приглушённо, потому что они структурно всегда нули, и это делает границу представимости видимой.

| Ввод | nanoTRX | В сети | Результат |
|---|---|---|---|
| `0.123456` | `123456000` | `123456 SUN` | отправляется |
| `2.5` | `2500000000` | `2500000 SUN` | отправляется |
| `0.123456789` | `123456789` | нет | отклоняется |

E2E-тесты используют `0.123456 TRX`, то есть максимально близкую к примеру из ТЗ сумму, которую сеть действительно способна провести точно.

## 11. Как запустить E2E

Тесты работают против живого стека: NestJS, PostgreSQL, TRON Nile и Chainstack.

**Предусловие.** Тесты сами переводят стартовый баланс проверяемым пользователям со служебного кошелька, поэтому его нужно один раз пополнить: возьмите адрес кошелька, чей приватный ключ лежит в `E2E_FUNDING_PRIVATE_KEY`, и пополните его на faucet [nile.tronscan.org](https://nile.tronscan.org) (Tools, затем Faucet). Хватает 1000 TRX на много прогонов. Свой служебный кошелёк можно сгенерировать командой `node scripts/generate-wallet.mjs`.

```bash
cd e2e
npm install
npm test
```

Настройки берутся из корневого `.env`: `E2E_API_URL`, `E2E_DATABASE_URL`, `E2E_FUNDING_PRIVATE_KEY`, `E2E_RESTART_CMD`.

Что проверяет каждый сценарий:

1. **Перевод между пользователями.** A отправляет B, тест дожидается статуса `confirmed` и сверяет балансы обеих сторон **по блокчейну**: получатель получил ровно отправленную сумму, у отправителя списалось не больше суммы плюс комиссия сети.
2. **Точность.** Сумма проходит API, базу и сеть без искажения: ответ API, значение в PostgreSQL и фактическое изменение баланса совпадают до последнего разряда, а сумма с девятью знаками отклоняется.
3. **Идемпотентность.** Два одновременных запроса с одним `Idempotency-Key` и повтор после подтверждения дают одну запись в базе, один `tx_hash` и одно движение средств.
4. **Отказоустойчивость.** Бэкенд перезапускается, пока транзакция в статусе `pending`; после перезапуска она доходит до `confirmed`, дубликатов не появляется, событие в outbox остаётся одно. Сценарий пропускается, если `E2E_RESTART_CMD` не задан.
5. **Резерв на комиссию.** Перевод всего баланса на неактивированный адрес отклоняется, потому что на комиссию и активацию не остаётся средств.

Unit-тесты бэкенда и фронтенда:

```bash
cd backend && npx jest
cd frontend && flutter test
```

## Kafka и согласованность

После подтверждения транзакции публикуется событие:

```json
{
  "event": "wallet.transaction.confirmed",
  "transaction_id": "...",
  "amount_nano": "500000000"
}
```

Consumer в `backend/src/consumer/main.ts` читает топик `wallet.transaction.confirmed`.

**Что будет, если запись в PostgreSQL прошла, а publish в Kafka не выполнился?**

Если писать в Kafka отдельным вызовом после коммита транзакции базы, между этими двумя действиями остаётся окно: процесс может упасть, брокер может оказаться недоступен. База уже говорит `confirmed`, а событие не ушло навсегда. Обратный порядок не лучше: publish до коммита рождает событие о том, чего в базе может так и не появиться. Двух источников истины без общей транзакции согласовать нельзя.

Решение это паттерн **Transactional Outbox**. Смена статуса на `confirmed` и запись события в таблицу `outbox_events` происходят в одной транзакции PostgreSQL: либо оба факта зафиксированы, либо ни одного. Отдельный воркер выбирает неопубликованные события, отправляет их в Kafka и проставляет `published_at`; при недоступности брокера он просто повторит попытку на следующем тике, ничего не потеряв.

Гарантия здесь at-least-once: если процесс упадёт между успешной отправкой и простановкой `published_at`, событие уедет повторно. Поэтому consumer обязан быть идемпотентным, то есть дедуплицировать по `transaction_id`. Сама смена статуса защищена от гонки условным обновлением `WHERE status = 'pending'`: событие в outbox пишется только если обновление действительно изменило строку, поэтому два воркера не породят два события об одной транзакции.

## Защита и ограничения

Частота запросов ограничена через `@nestjs/throttler`: вход 5 попыток в минуту, регистрация 10 в минуту, отправка 10 в минуту на пользователя. Счётчики живут в памяти процесса, поэтому сбрасываются при рестарте и не общие для нескольких реплик; для боевой установки их следует вынести в Redis, как и счётчик версий long-polling.

## Деплой

```bash
bash scripts/deploy.sh
```

Скрипт собирает фронтенд, выкладывает на сервер отслеживаемые Git файлы вместе со сборкой и `.env`, затем пересобирает и перезапускает стек. Приложение отвечает на `http://test-wallet.loc`; чтобы имя резолвилось, добавьте в hosts строку:

```
188.127.237.116 test-wallet.loc
```

HTTPS не настраивается: для домена `.loc` сертификат получить негде, а самоподписанный только мешал бы проверке.

Из этого следует одна неочевидная деталь. На незащищённом origin браузер не отдаёт `navigator.clipboard`, поэтому штатный `Clipboard.setData` во Flutter падает с ошибкой, и кнопка COPY молча не работает. Копирование сделано с запасным путём: сначала пробуется системный Clipboard API, а если его нет, используется скрытое поле и `document.execCommand('copy')`, который на HTTP доступен. При HTTPS сработает первый путь, менять ничего не придётся.

## Как пополнить кошелёк без faucet

Faucet Nile ограничивает выдачу по времени и защищён капчей, поэтому обращаться к нему повторно не нужно. Достаточно один раз пополнить служебный кошелёк, а дальше раздавать TRX с него:

```bash
node scripts/fund.mjs <адрес> [сумма в TRX]
```

Скрипт берёт ключ отправителя из `E2E_FUNDING_PRIVATE_KEY`, проверяет адрес и остаток и печатает хеш перевода. E2E-тесты пополняют создаваемых пользователей тем же способом, поэтому их можно прогонять сколько угодно раз.
