# Mini TRON Wallet

Кастодиальный кошелёк TRON в тестовой сети Nile: регистрация создаёт пользователю адрес, приложение показывает баланс и историю, позволяет отправить TRX и следит за подтверждением транзакции в блокчейне.

**Стек:** Flutter Web + Riverpod · NestJS + TypeScript · PostgreSQL + Prisma · TRON Nile через Chainstack · Kafka · Docker Compose.

```
Flutter Web ──REST──> NestJS ──> PostgreSQL
                        │
                        ├──> Chainstack ──> TRON Nile
                        └──> Kafka (outbox)
```

Фронтенд не обращается к базе и к Chainstack напрямую и никогда не получает приватные ключи: он знает только про REST API бэкенда.

## 1. Как запустить проект

Нужны Docker и Docker Compose. Всё остальное поднимается контейнерами.

```bash
cp .env.example .env
```

Заполните в `.env`:

| Переменная | Чем заполнить |
|---|---|
| `JWT_SECRET` | `openssl rand -hex 32` |
| `WALLET_MASTER_KEY` | `openssl rand -hex 32` — ровно 64 hex-символа |
| `CHAINSTACK_ENDPOINT` | `https://tron-nile.core.chainstack.com` |
| `CHAINSTACK_API_KEY` | ключ проекта Chainstack |

Соберите фронтенд и поднимите стек:

```bash
cd frontend && flutter build web --release && cd ..
docker compose up -d --build
```

Поднимутся пять сервисов: `postgres`, `kafka`, `backend` (применяет миграции при старте), `consumer`, `frontend` (nginx отдаёт собранный Flutter и проксирует `/api` на бэкенд). Приложение открывается на `http://localhost`.

### Разработка без Docker

Если Docker недоступен локально, базу и Kafka можно держать на сервере и пробросить порты:

```bash
bash scripts/tunnel.sh
```

После этого `DATABASE_URL` и `KAFKA_BROKERS` со значением `localhost` работают с удалёнными сервисами.

## 3. Как запустить Flutter Web

```bash
cd frontend
flutter pub get
flutter run -d chrome --dart-define=API_URL=http://localhost:3000
```

`API_URL` нужен только в разработке, когда бэкенд слушает отдельный порт. Продакшен-сборка использует значение по умолчанию `/api`, то есть ходит на тот же origin через nginx:

```bash
flutter build web --release
```

### Как устроен Riverpod

Состояние живёт в трёх провайдерах (`frontend/lib/providers/`):

- `authProvider` — `Notifier<AuthState>`: восстановление сессии по сохранённому JWT, вход, регистрация, выход. Провайдер живёт всё время работы приложения, поэтому сессия переживает навигацию.
- `walletProvider` — `Notifier<WalletState>` с `isAutoDispose: true`: баланс, история и отправка. Внутри `build()` заводится таймер на 5 секунд, который опрашивает бэкенд; `ref.onDispose` останавливает таймер, когда экраны кошелька закрыты, чтобы не опрашивать API впустую.
- `themeProvider` — переключение светлой и тёмной темы с сохранением выбора.

Маршрутизация на `go_router`: экраны `/login` и `/register` открыты, а `/wallet`, `/send` и `/transactions` живут внутри `ShellRoute` с общей шапкой. Роутер создаётся один раз, а на изменения сессии реагирует через `refreshListenable` — так навигация не сбрасывается при входе и выходе.

## 5. Как запустить PostgreSQL

```bash
docker compose up -d postgres
cd backend && npx prisma migrate deploy
```

### Почему Prisma

ТЗ разрешает любую ORM, выбрана Prisma по трём причинам. Миграции здесь первичны: схема описывается декларативно, `prisma migrate` порождает обычный SQL-файл, который лежит в репозитории и разворачивается одной командой. Сгенерированный клиент типизирует запросы вплоть до имён колонок, поэтому переименование поля ломает сборку, а не продакшен. И `BigInt` из схемы отображается в `bigint` TypeScript без промежуточных чисел с плавающей точкой — для денег это решающий аргумент.

### Схема

- `users` — `id`, `email` (уникальный), `password_hash`, `created_at`.
- `wallets` — `user_id` (уникальный, внешний ключ), `address` (уникальный), `encrypted_private_key`.
- `transactions` — `id`, `user_id` (внешний ключ), `direction`, `amount`, `address`, `status`, `tx_hash`, `idempotency_key`, `created_at`.
- `outbox_events` — события для Kafka.
- `sync_state` — последний просканированный блок.

Ограничения, которые несут смысл: `UNIQUE(user_id, idempotency_key)` защищает от повторной отправки, `UNIQUE(user_id, tx_hash, direction)` — от повторной записи одного и того же перевода, индексы по `status` и по `(user_id, created_at DESC)` обслуживают воркер подтверждений и выдачу истории.

## 6. Как создаётся TRX wallet

При `POST /auth/register` бэкенд генерирует пару ключей через TronWeb, сохраняет base58-адрес в `wallets.address`, шифрует приватный ключ и кладёт в `wallets.encrypted_private_key`. Пользователь получает JWT и свой адрес. Все обращения к сети идут через Chainstack: `CHAINSTACK_ENDPOINT` и `CHAINSTACK_API_KEY` собираются в `fullHost` клиента TronWeb.

## 7. Как хранятся private keys

Приватный ключ шифруется AES-256-GCM мастер-ключом `WALLET_MASTER_KEY` из `.env`. В базе лежит строка `iv.tag.ciphertext` в base64: случайный вектор инициализации на каждое шифрование и тег аутентификации, из-за которого подмена шифротекста приводит к ошибке расшифровки, а не к молчаливому мусору.

Ключ расшифровывается только в момент подписи транзакции и не покидает бэкенд: его нет в ответах API, нет во Flutter и нет в логах. В Git попадает только `.env.example` без значений.

## 8. Как отправляется TRX

`POST /wallet/send` выполняет шаги по порядку:

1. проверяет JWT;
2. проверяет корректность адреса получателя;
3. разбирает сумму и отвергает то, что сеть не сможет провести;
4. если такой `Idempotency-Key` уже был — возвращает прежнюю транзакцию и на этом останавливается;
5. сверяет баланс;
6. создаёт запись со статусом `pending`;
7. подписывает транзакцию и **сохраняет `tx_hash` до отправки в сеть**;
8. отправляет транзакцию и возвращает ответ фронтенду.

Порядок седьмого и восьмого шагов выбран намеренно: если соединение оборвётся во время отправки, хеш уже сохранён, и воркер подтверждений сам выяснит судьбу транзакции по сети. Ошибка подписи переводит запись в `failed`, ошибка сети оставляет `pending`.

Входящие переводы находит отдельный воркер: он идёт по новым блокам, отбирает переводы на известные адреса и заводит записи с направлением `incoming`.

## 9. Как работает idempotency

Заголовок `Idempotency-Key` обязателен. Ключ пишется в ту же строку таблицы `transactions`, что и сама операция, под уникальным индексом `UNIQUE(user_id, idempotency_key)`.

Повторный запрос с тем же ключом находит существующую запись и возвращает её, не обращаясь к блокчейну. Если два запроса пришли одновременно и оба не нашли записи, вставку выиграет ровно один: второй получит ошибку уникальности `P2002`, перечитает запись победителя и вернёт её. Подписывает и отправляет транзакцию только тот запрос, который создал строку, поэтому в сети всегда оказывается одна транзакция.

Фронтенд генерирует ключ один раз на попытку отправки и переиспользует его при повторе, так что повторное нажатие кнопки не создаёт второй перевод.

## 10. Как обрабатывается конвертация TRX

Внутренняя единица — nanoTRX, `1 TRX = 1 000 000 000 nanoTRX`, как требует ТЗ. Суммы везде целые и передаются строками: во Flutter это `BigInt`, в JSON — строка, в NestJS — `bigint`, в PostgreSQL — `bigint`. Чисел с плавающей точкой в денежном пути нет ни в одном слое.

**Важное расхождение, о котором стоит сказать прямо.** Сеть TRON оперирует единицей SUN, где `1 TRX = 1 000 000 SUN`, то есть поддерживает шесть знаков после запятой, а не девять. Сумма вида `0.123456789 TRX` физически не может быть проведена в TRON. Поэтому система устроена так:

- формат ТЗ сохранён: внутри всё считается в nanoTRX и отображается с девятью знаками;
- пересчёт nanoTRX ↔ SUN выполняется только в блокчейн-адаптере, на границе с сетью;
- сумма, не кратная 1000 nanoTRX, отклоняется с ошибкой `AMOUNT_NOT_REPRESENTABLE_ON_CHAIN` до всякого обращения к сети — лучше честно отказать, чем отправить не то, что попросили;
- интерфейс принимает не более шести знаков и показывает последние три разряда суммы приглушённо: они структурно всегда нули, и это делает границу представимости видимой.

| Ввод | nanoTRX | В сети | Результат |
|---|---|---|---|
| `0.123456` | `123456000` | `123456 SUN` | отправляется |
| `2.5` | `2500000000` | `2500000 SUN` | отправляется |
| `0.123456789` | `123456789` | — | отклоняется |

E2E-тесты используют `0.123456 TRX` — максимально близкую к примеру из ТЗ сумму, которую сеть действительно способна провести точно.

## 11. Как запустить E2E

Тесты работают против живого стека: NestJS, PostgreSQL, TRON Nile и Chainstack.

**Предусловие.** Тесты сами переводят стартовый баланс проверяемым пользователям со служебного кошелька, поэтому его нужно один раз пополнить: возьмите адрес кошелька, чей приватный ключ лежит в `E2E_FUNDING_PRIVATE_KEY`, и пополните его на faucet [nile.tronscan.org](https://nile.tronscan.org) (Tools → Faucet). Хватает 1000 TRX на много прогонов. Свой служебный кошелёк можно сгенерировать командой `node scripts/generate-wallet.mjs`.

```bash
cd e2e
npm install
npm test
```

Настройки берутся из корневого `.env`: `E2E_API_URL`, `E2E_DATABASE_URL`, `E2E_FUNDING_PRIVATE_KEY`, `E2E_RESTART_CMD`.

Что проверяет каждый сценарий:

1. **Перевод между пользователями** — A отправляет B, тест дожидается статуса `confirmed` и сверяет балансы обеих сторон **по блокчейну**: получатель получил ровно отправленную сумму, у отправителя списалось не больше суммы плюс комиссия сети.
2. **Точность** — сумма проходит API, базу и сеть без искажения: ответ API, значение в PostgreSQL и фактическое изменение баланса совпадают до последнего разряда, а сумма с девятью знаками отклоняется.
3. **Идемпотентность** — два одновременных запроса с одним `Idempotency-Key` и повтор после подтверждения дают одну запись в базе, один `tx_hash` и одно движение средств.
4. **Отказоустойчивость** — бэкенд перезапускается, пока транзакция в статусе `pending`; после перезапуска она доходит до `confirmed`, дубликатов не появляется, событие в outbox остаётся одно. Сценарий пропускается, если `E2E_RESTART_CMD` не задан.

Unit-тесты бэкенда и фронтенда:

```bash
cd backend && npx jest
cd frontend && flutter test
```

## Kafka и согласованность

После подтверждения транзакции публикуется событие:

```json
{
  "event": "wallet.transaction.confirmed",
  "transaction_id": "...",
  "amount_nano": "500000000"
}
```

Consumer в `backend/src/consumer/main.ts` читает топик `wallet.transaction.confirmed`.

**Что будет, если запись в PostgreSQL прошла, а publish в Kafka не выполнился?**

Если писать в Kafka отдельным вызовом после коммита транзакции базы, между этими двумя действиями остаётся окно: процесс может упасть, брокер — оказаться недоступен. База уже говорит `confirmed`, а событие не ушло навсегда. Обратный порядок не лучше: publish до коммита рождает событие о том, чего в базе может так и не появиться. Двух источников истины без общей транзакции согласовать нельзя.

Решение — паттерн **Transactional Outbox**. Смена статуса на `confirmed` и запись события в таблицу `outbox_events` происходят в одной транзакции PostgreSQL: либо оба факта зафиксированы, либо ни одного. Отдельный воркер выбирает неопубликованные события, отправляет их в Kafka и проставляет `published_at`; при недоступности брокера он просто повторит попытку на следующем тике, ничего не потеряв.

Гарантия здесь — at-least-once: если процесс упадёт между успешной отправкой и простановкой `published_at`, событие уедет повторно. Поэтому consumer обязан быть идемпотентным — дедуплицировать по `transaction_id`. Сама смена статуса защищена от гонки условным обновлением `WHERE status = 'pending'`: событие в outbox пишется только если обновление действительно изменило строку, поэтому два воркера не породят два события об одной транзакции.

## Деплой

```bash
bash scripts/deploy.sh
```

Скрипт собирает фронтенд, выкладывает на сервер отслеживаемые Git файлы вместе со сборкой и `.env`, затем пересобирает и перезапускает стек. Приложение отвечает на `http://test-wallet.loc`; чтобы имя резолвилось, добавьте в hosts строку:

```
188.127.237.116 test-wallet.loc
```

HTTPS не настраивается: для домена `.loc` сертификат получить негде, а самоподписанный только мешал бы проверке.
